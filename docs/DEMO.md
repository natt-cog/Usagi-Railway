# デモ台本: 鉄道 電力管理・車両保守システムの保守と移行

対象: 社会インフラ (鉄道・電力) システムの保守を担当されている方
所要: 35〜40 分 (ライブ 15 分 + 事前実行の結果 20 分)
題材: URMS (架空の「うさぎ鉄道 電力・車両保守システム」。Spring Boot 1.5 / Java 8 / JSP, C と COBOL の夜間バッチ)

伝えたいこと
1. 設計書が古い / ないシステムでも、コードから仕様を起こせる
2. 客先からの改造依頼を、影響調査 → 修正 → 試験まで一気通貫で進められる
3. 移行は「出力が 1 バイトも変わらない」ことをテストで示しながら進められる
4. 納入先ごとに分かれた版へ、同じ修正を並列で当てられる

## 2. 保守改修 (ライブ 10〜15 分): 客先からの改造依頼

依頼内容 (客先からのメール風に読み上げる)
> き電区分所や支線の変電所では、本線と同じ閾値だと誤警報が多い。
> 警報の閾値 (電圧低下・過電流) を変電所ごとに設定できるようにしてほしい。電力日報の回数も同じ閾値で数えること。

プロンプト (Devin セッション)
```
URMS に「警報閾値を変電所ごとに設定する」改修を入れてください。
- 影響調査を先に日本語でまとめる (Java, JSP, DB, C バッチ URPWD01, テスト)
- SUBSTATION に閾値列を追加 (Flyway V3)。未設定の変電所は従来の 1350V / 4000A
- 警報判定、電力日報、C バッチ URPWD01 を同じ閾値で動かす (C は入力ファイルで閾値を受け取る)
- SS04 卯月変電所は電圧低下 1300V にする
- 試験項目表を作り、JUnit と C のゴールデンテストを更新。CBatchParityTest は維持
- PR を作成
```

見どころ
- 影響調査で **C バッチまで** 洗い出せるか (Java だけ直すと日報の回数がずれる)
- `CBatchParityTest` によって Java と C の判定が食い違わないことを保証している
- 画面で確認: 変電所 SS04 の計測値の強調表示, 電力日報の回数

詰まったら: `demo/reset.sh demo/1-threshold --start` で完成版に切り替える

## 3. 移行 (事前実行 10 分): 結果を見せる

### 3-1. C / COBOL バッチを Java へ
- 事前実行のプロンプト
  ```
  batch/c/urpwd01.c と batch/cobol/URINS01.cbl を Java (Spring Batch は使わず既存サービス) に置き換え、
  夜間ジョブとして実行できるようにしてください。CBatchParityTest と CobolParityTest を契約とし、
  出力が 1 バイトも変わらないことを示してください。
  ```
- 見せるもの: PR の差分, ゴールデンテストが成功している CI, 置き換えた C / COBOL の行数

### 3-2. Spring Boot 1.5 / Java 8 → Spring Boot 3 / Java 21
- 子セッションを並列で走らせる (domain / repository / service / security / web+api / tests)
- 見せるもの: Devin Boards のチケット分解, 並列の PR, 統合後に `mvn test` 33 件が全て成功
- 移行しても `DAILY_20261005.DAT` と `INSPDUE.DAT` が変わらないこと

## 質疑で出やすい質問

| 質問 | 回答の方向性 |
